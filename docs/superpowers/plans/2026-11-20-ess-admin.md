# ESS Admin Area (Stage E) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A signed-in `/admin` area on the new ESS website where ESS Admin and ESS Staff handle AC enquiries (send prices), see website requests, manage ACs, edit and publish website text and business details, choose which services and pincodes the site shows, and (admins only) give people access.

**Architecture:** The PYS API for all of this already exists (`/api/v1/ess/admin/*`, Stage B + plan 3). Each call needs the ESS server's signature (already built: `lib/pys/client.ts`) plus the signed-in person's Supabase access token in `X-PYS-Actor-Token`. The ESS site signs people in with the same Supabase accounts as PYS (email + password) using `@supabase/ssr` cookies. Server components read admin data; changes go through Server Actions that call PYS and then `revalidateTag` so the public pages update at once. Admin pages live in their own route group with their own layout: same colour tokens and glass cards, no photo banner, no floating buttons, no public header or footer.

**Tech Stack:** Next.js 16.4.6 App Router (`cacheComponents`, Proxy), React 19.3, Tailwind 4, `@supabase/ssr` + `@supabase/supabase-js` (new), zod 4, vitest 5 + Testing Library, Playwright MCP.

**Spec:** No separate design doc. The requirements are Phase 2 "Stage E" in the redesign plan (`C:\Users\aayup\.claude\plans\do-a-full-research-splendid-flurry.md`, section "Phase 2 — REDESIGNED" and "2.4 ESS admin console"), plan 3 (`C:\Users\aayup\.claude\plans\in-the-ac-section-nested-fox.md`, AC enquiry flow), and design spec §7–§8 (`docs/superpowers/specs/2026-11-19-ess-website-design.md`: "/admin uses the same colour tokens and glass cards … but no photo banner or effects"). The owner reviews this plan as the spec.

## Global Constraints

- Plan 2's Global Constraints still apply: repo, branch `phase-2-ess-rebuild`, commit trailer, read `web/node_modules/next/dist/docs/` before any Next API, vitest from PowerShell at the `C:\` path, colour tokens, 44px targets, Archivo only, plain English.
- **Roles:** ESS Staff can see everything, send AC prices, edit products, and save drafts of website text. Only ESS Admin can publish business details and legal text (`business.*`, `legal.*`), change services shown and pincodes, and manage users. A PYS Admin is automatically an ESS Admin. PYS enforces all of this; the site also hides buttons a person cannot use.
- **Security:** the Supabase **service role key never reaches the ESS site**. ESS only uses the public URL and the publishable (anon) key. Admin pages and actions are never cached, never prerendered with user data, and send `Cache-Control: no-store`. `/admin` has `robots: noindex`. A sign-in error never says whether an email exists.
- **Customer data:** customer phone and email appear only in the AC enquiries and Requests screens, behind sign-in. They are never logged and never put in URLs.
- **Prices:** an AC price entered by the seller is per AC, incl. GST, > 0 and ≤ ₹1,00,00,000 (PYS rule). Product price must be ≤ MRP when both are given (PYS rule, mirrored in the form).
- **No new claims:** admin screens are internal, but any text they publish goes to the public site. The editors show a reminder of the owner's rule: no arrival times, no "genuine/OEM", no "certified/verified technicians", no invented reviews.
- **Local development:** the mock PYS gets in-memory admin endpoints. A **dev-only sign-in** (`/admin/login` "Sign in as test admin") exists only when `NODE_ENV !== 'production'` **and** `PYS_API_URL` points to `localhost`. It sends the fixed token `dev-admin-token`, which only the mock accepts. Tested so it can never switch on in production.

## Review Focus

1. **Session ends or the role is removed mid-use** → the next action shows "Please sign in again" or "You don't have access to this", never a crash or a silent failure. Tests: T2 (`adminRequest` maps PYS 401/403), T4 (quote action after 401 redirects to login).
2. **Double click on "Send price" / "Publish"** → one PYS call. Test: T4, T6 (button disabled while pending; action ignores repeat).
3. **Staff opens an admin-only screen by URL** (`/admin/users`, `/admin/areas`) → friendly "Only an ESS Admin can do this" page, no data. Test: T7, T8.
4. **Wrong input**: price `0`, `abc`, `1,50,000` typed with commas, MRP below price, pincode prefix `40 0`, offer end date in the past → clear field message, nothing sent. Tests: T4 (`parseRupees`), T5, T7, T6.
5. **The public site shows stale data after an admin change** → after each successful change the matching cache tag is refreshed (`products`, `content`, `catalog`, `areas`). Test: T5/T6/T7 (action calls `revalidateTag` with the right tag).
